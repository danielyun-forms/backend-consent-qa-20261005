Key findings

These observations failed within their stated test boundaries:

  • FM-01: A retryable unsubscribe failure retries the whole message — An escaping UnableToObtainLockException invokes the real retry helper/chariot_reject. However, an exhausted retryable workflow error is swallowed by modify_permissions's default configuration: attempted DENY returns normally, does not invoke attempt_retry or consumer error/drop counters, and the prior ALLOW persists.
  • OB-02: Consumer drops are visible and distinguishable — Real permission-service fault probes confirmed both terminal and exhausted-retryable DENY failures leave the prior stored ALLOW unchanged. Sentry capture fires, but neither consumer StatsD nor retry StatsD increments and no consumer retry is requested. The expected distinguishable consumer error counter therefore does not cover these failed revocations. The no-email drop counter is separately verified by the consumer tests.
  • AC-05: An email block with no marketing and no tracking is rejected — Both inputs reject with HTTP 400 invalid. Empty email matches the sheet message. Unknown-only input instead reports: 'unrelated' is not a valid field for the resource 'email_subscription_parameters'. Thus the exact-message assertion fails for the unknown-key variant.

Behavior requiring review

A pass can confirm documented behavior; it does not approve the behavior as safe or production-ready.

  • FM-02: A non-retryable unsubscribe failure DROPS the revocation — A terminal permission workflow failure reports to Sentry but returns normally with no consumer retry or consumer error/drop counters; the prior persisted click ALLOW remains after attempted DENY. Separately, an unexpected ValueError escaping modify_permissions propagates, so not every nonretryable exception is silently swallowed.
  • SE-01: DENY is written before the bot and abuse checks run — Protections now execute inside subscribe before the separate tracking batch. A real subscribe call whose protection decision returns blocked exits normally; the adapter then still applies either ALLOW or DENY. Both operations were separately exercised. A raised subscribe failure instead prevents tracking. The old denial-first ordering is obsolete, but the protection-return result does not gate tracking writes.
  • SE-02: A third party cannot flip tracking for an arbitrary email — The public onsite authentication accepts an anonymous request on the valid client host/path without credentials or an email ownership proof. Synthetic tracking API requests are accepted in the adapter checks. Marketing consent is not implicitly included in explicit tracking-only payloads. An arbitrary-email tracking operation is not prevented by identity authentication.
